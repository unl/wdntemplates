Plugin Auto-Loader

The plugin auto-loader serves as the modern replacement for RequireJS, which was previously utilized in version 5.3 of the framework.

Instead of forcing a heavy, bundled asset payload on every visitor, the auto-loader dynamically scans the DOM on page load and fetches the JavaScript and CSS dependencies required only for the components present on the page. To maximize efficiency and optimize load times, the auto-loader pulls these plugins and components in parallel.

Note: Using the auto-loader is completely optional. It can be disabled or entirely removed from your application environment; however, doing so means you must manually import the JavaScript modules and link the corresponding CSS stylesheets for any interactive component you place on your pages.

How It Works

To keep assets modular, every framework component has its core logic and styling isolated into standalone files. Manually tracking and declaring these imports for every unique page layout would be incredibly tedious. The framework abstracts this through a two-layer architecture:

The Plugin Layer

Each component is paired with a specific plugin wrapper. When triggered, the plugin executes an initialize function, returning a Promise that resolves once all underlying script and style dependencies are safely loaded into the browser environment.

Once ready, a target element's DOM reference can be passed directly to the plugin's loadElement method. This instantiates the core component class, hooks it to that element, and returns the running class instance.

The Auto-Loader Layer

The auto-loader coordinates all available plugins. It reads their defined criteria (such as a specific CSS selector), queries the DOM for matches, and automates the element selection and initialization steps entirely behind the scenes.

Furthermore, the auto-loader implements a MutationObserver. This actively watches the DOM tree for any elements injected dynamically after initial page render (e.g., content loaded via AJAX), ensuring newly added components are hydrated automatically.

Not all the JS components in the framework are loaded via the auto-loader. Some like analytics or the primary navigation need to load their functionality prior to the auto-loader loading. These components can be found in header-global-1.js and nav-container-2.js.

Configuration

There is a lot of ways to configure the auto-loader prior to it running on the page. The auto-loader script can be found defined in js-body global include. This is at the very bottom of the page after the footer. The default configurations are done in the head-2.js script which is found the head-2 global include. So as long as you adjust the configurations between the default being set and the auto-loader script starting you should be good.

Global Settings

The auto-loader config lives in window.UNL.autoLoader.config. This includes config for how the auto-loader runs as well as the plugins it uses to listen for and load components. Here are some of configuration settings for the auto-loader:

  • enabled (Boolean): Determines whether the auto-loader should parse and execute.
  • watch (Boolean): Dictates whether the MutationObserver should watch for dynamically injected elements.
  • globalOptInSelector (String): A global CSS selector that an element must feature before the auto-loader is allowed to process it.
  • globalOptOutSelector (String): A global CSS selector that acts as an exclusion ruleset; matching elements will be skipped entirely.

Lifecycle Events & Callbacks

The auto-loader dispatches standard DOM events, specifically autoLoaderPreLoad and autoLoaderPostLoad, to mark its initialization timeline. You can wire native listeners directly to the document: 

document.addEventListener('autoLoaderPostLoad', () => {
    console.log('Framework auto-loader is fully ready.');
});

Alternatively, you can register callbacks using the utility method: window.UNL.autoLoader.onLoad(callbackFunction). If registered before the system completes loading, the callback function is securely queued and executed the instant initialization finishes. If registered after the framework is already live, the callback fires immediately.

Plugins

Each plugin is defined in the auto-loader configuration and includes where the plugin code lives an any other custom configurations that plugin needs. The plugins config lives in window.UNL.autoLoader.config.plugins Here are some of configuration settings for the plugins:

  • url (String): The path/url pointing to where the plugin code file lives.
  • onPluginLoadedElement (Function): A callback triggered every time the auto-loader successfully hydrates a matching element for this specific plugin.
  • customConfig (Object): An arbitrary configuration payload passed downstream into the plugin during initialization.
  • optInSelector / optOutSelector (String): Plugin-specific selector rules that restrict or grant execution permissions independently of global settings.

If you wanted to remove any of the plugins from the default autoloader configuration you can simply delete the plugin's configuration from the auto-loader config prior to the auto-loader running. For example here is the code to remove the UNLDialog plugin: delete window.UNL.autoLoader.config.plugins.UNLDialog.

Auto-Loader, Plugin & Component Data

Once initialization wraps up, you can inspect active plugins and their associated states via window.UNL.autoLoader.plugins. This namespace contains state logs tracking whether the plugin script successfully completed its fetch, references to the imported module definitions, and an array mapping active class instances back to their respective DOM nodes.

Because filtering through raw plugin state arrays to locate a single element's instance can be tricky, a cleaner utility method is provided in /wdn/templates_6.1/js/lib/unl-utility.js called getClassInstance.

This function relies on the fact that all UNL components register their running instances to a global dictionary registry at window.UNL.classes, and returns a clean promise that resolves the moment the instance is safe to interact with: 

import { getClassInstance } from '/wdn/templates_6.1/lib/unl-utility';

// Resolves once the specific element is fully hydrated and ready for programmatic control
const dialogClass = await getClassInstance('my-dialog');
dialogClass.open();
